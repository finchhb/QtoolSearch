# Поиск и RAG для товарного каталога

Каталог режущего инструмента как эталон: десятки тысяч позиций, артикулы, ISO-коды, 1С как источник цен и остатков, сайт, LLM. Правила переносимы на любой товарный каталог той же природы.

## Принципы (приоритет при конфликтах)

1. **Масштаб определяет архитектуру.** До ~1M позиций не нужны GPU-индексы, квантование и шардирование.
2. **Артикулы, размеры и коды ищутся точно** — лексикой и фильтрами. Эмбеддинги нужны для смысла и свободных формулировок.
3. **LLM не источник фактов о товарах.** Цены, остатки, характеристики — только из 1С и каталога.
4. **Любое изменение сначала меряется на золотом наборе**, потом внедряется.

При расхождении с «базовой матрицей» (PQ/IVF, DESM, RAG-Sequence, ROUGE/BLEU) действуют правила этого документа — см. раздел «Устаревшее».

## 1. Архитектура по масштабу

- До ~1M векторов: flat-индекс или HNSW. 100k × 1024d float32 ≈ 400 МБ, точный перебор на CPU 10–50 мс. 1M × 1024d ≈ 4 ГБ (int8 ≈ 1 ГБ).
- HNSW: `M = 16–32`, `efConstruction ≈ 200`, `efSearch 64–128`; recall@10 обычно 0,95–0,99 к точному поиску.
- Хранение: Postgres + pgvector, Qdrant или OpenSearch. BM25 и векторы в одном хранилище упрощают гибрид.
- IVF-PQ, GPU-репликация/шардирование, свои CUDA-ядра — от ~50–100M векторов или при жёстком QPS. Ниже этого — лишняя сложность.

## 2. Пайплайн запроса

1. **Нормализация**: регистр, пробелы, дефисы, точки, слэши; кириллические двойники латиницы (С/C, Н/H, М/M, Т/T, Р/P, А/A, В/B, Е/E, К/K, О/O, Х/X) и обратно. Единицы к одному виду: «Ø10», «d10», «10 мм» → диаметр 10.
2. **Разбор в фильтры**: LLM с JSON-схемой (тип инструмента, ISO-код, размеры, материал заготовки, покрытие, бренд, наличие). Каждое значение валидировать по справочнику каталога; невалидное выбрасывать, не додумывать.
3. **Гибридный поиск**: BM25 по названию, артикулу, бренду, атрибутам (для артикулов — n-граммы или префиксы) + вектор по описанию. Слияние через RRF: `score = Σ 1 / (60 + rank)`.
4. **Фильтры двух видов**: жёсткие (тип, диаметр, посадка, ISO-форма) отрезают; мягкие (бренд, покрытие) только повышают ранг.
5. **Реранкер** (cross-encoder, напр. bge-reranker-v2-m3) на топ-30–50 — включать только при приросте nDCG на золотом наборе; на CPU замерить задержку.
6. **Ответ**: позиции с артикулом и ссылкой. LLM формулирует текст; цена и остаток — из 1С.

Детерминированный слой всегда должен отвечать сам (артикул, код, точные фильтры) — без LLM и эмбеддингов. LLM опционален и работает ревьюером/разборщиком, а не единственным путём.

## 3. Артикулы и ISO-обозначения

- ISO 1832 разбирается детерминированным парсером. Пример: `CNMG 12 04 08` = форма C, задний угол N, допуск M, тип G (отверстие, стружколом с двух сторон), размер 12 (≈12,7 мм), толщина 04 (4,76 мм), радиус 08 (0,8 мм). Толщина бывает вида `T3` (3,97 мм) — `CCMT 09T304`.
- Хвост (`-PM`, марка сплава) зависит от производителя — хранить отдельным полем, не запихивать в код.
- Разобранные поля хранить атрибутами и фильтровать по ним: так находятся все `CNMG1204` любого бренда и ближайшие аналоги.
- **Эмбеддинги не различают близкие коды и числа** (`120404` и `120408` для них почти одно и то же). Размеры — только лексика/фильтры.
- Кроссы между брендами (Deskar, ZZKLT/Kelite, Sekira и аналоги западных) — таблица эквивалентов; работает и как синонимы, и как блок «аналоги».
- Русская морфология: лемматизация (pymorphy3 или Snowball в OpenSearch). Синонимы: пластина/вставка/insert, фреза/mill, сверло/drill, державка/резец, токарный/turning. Учитывать латиницу и кириллицу в названиях брендов.

## 4. Эмбеддинги

- ru + смешанный ru/en: bge-m3 (1024d, dense + sparse, длинный контекст), multilingual-e5-large или API (GigaChat, Yandex). Выбор — по Recall@10 на золотом наборе, не по рейтингам.
- Эмбеддить «карточку»: тип, ключевые атрибуты, назначение, материалы, краткое описание. Не голый артикул.
- Смена модели эмбеддингов = полная пересборка индекса.

## 5. RAG: консультант по применению

Нужен для вопросов вида «чем чистово точить 12Х18Н10Т», а не для поиска позиций.

- База знаний: техстатьи, рекомендации производителей, таблицы режимов. Чанки 300–800 токенов, перекрытие 10–15%, метаданные (бренд, материал, операция, источник).
- В промпт — топ-5–8 чанков, обязательные ссылки на источник. Нет контекста — ответ «в базе нет данных», без догадок.
- Режимы резания и применимость — только из таблиц производителя. LLM не считает и не подставляет из головы: брак и поломки потом на нас.
- Обновление без дообучения: индекс версионируется, дельта из 1С и сайта по расписанию, полная пересборка при смене модели.

## 6. Оценка качества

- Золотой набор 150–300 реальных запросов из логов сайта и от менеджеров: по артикулу, по ISO-коду, описательные, с опечатками, на английском, «такого нет».
- Разметка 0/1/2 (не подходит / подходит / идеально) минимум на топ-20.
- Retrieval: Hit@1 и MRR@10 для артикульных; Recall@10 и nDCG@10 для описательных; доля нулевой выдачи. Стартовые ориентиры: Hit@1 ≥ 95% на артикулах, Recall@10 ≥ 80–85% на описательных; корректировать по факту.
- Разбор запроса: F1 по каждому полю фильтра.
- RAG: faithfulness, context precision/recall, answer relevance, доля корректных отказов. LLM-as-judge калибровать на ~50 ручных оценках.
- Каждое изменение (модель, веса гибрида, реранкер, пороги) — прогон «до/после» на наборе, а не на глаз.

## 7. Эксплуатация

- Бюджет задержки: поиск < 100–200 мс; LLM-разбор 0,5–2 с с кэшем по нормализованному запросу; реранкер — по замеру.
- Логи: запрос, разобранные фильтры, топ-10, клики, добавления в корзину. Это будущий золотой набор.
- Безопасность: не отдавать закупочные цены и внутренние поля — ограничение на уровне полей поиска, а не промпта. Текст описаний и отзывов считать недоверенным (prompt injection). ПДн клиентов не отправлять во внешние API (152-ФЗ).
- 1С — источник истины по цене и остаткам. В индексе только редко меняющееся, остальное подтягивать при выдаче.

## 8. Порядок внедрения

1. Золотой набор, нормализация, парсер ISO, BM25. Замер baseline.
2. LLM-разбор запроса в фильтры с валидацией по справочнику.
3. Векторы + RRF. Сравнение с baseline.
4. Реранкер — только если есть прирост.
5. RAG-консультант на базе знаний.
6. Логи, мониторинг, регулярный перезамер.

Не перескакивать шаги: без baseline любая «умная» надстройка недоказуема.

## Устаревшее (из базовой матрицы, не применять в этом масштабе)

- **PQ, IVF-ADC, GPU-репликация и шардирование, регистры/shared memory в CUDA** — для миллиардов векторов. Возвращаться при >50–100M.
- **DESM и IN/OUT-векторы Word2Vec, Topical/Typical** — исторический материал, заменён современными bi-encoder'ами.
- **RAG-Sequence / RAG-Token, совместное обучение ретривера и генератора** — недоступно с API-моделями, выигрыш мал.
- **ROUGE/BLEU для RAG** — заменены faithfulness и context precision/recall.
- **«Протолкнуть всю базу через тяжёлую нейросеть»** — только многоступенчатый отбор: дешёвый L1 (BM25/ANN) → тяжёлый L2 (cross-encoder) на топ-30–50.

## Чек-лист перед выдачей решения

- [ ] Есть замер baseline и золотой набор (или явно сказано, что его нет и это первый шаг).
- [ ] Точные запросы (артикул/код/размер) идут детерминированным путём, без эмбеддингов.
- [ ] Жёсткие и мягкие фильтры разделены.
- [ ] Цены и остатки берутся из 1С, не из LLM и не из индекса.
- [ ] Для RAG есть отказ «нет данных» и ссылки на источники.
- [ ] Задержка и стоимость укладываются в бюджет; тяжёлые компоненты включаются по измеренному приросту.
